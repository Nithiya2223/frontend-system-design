Chapter 1: Networking

Chapter at a glance

  1. Every frontend feature is a conversation over a network. Its speed is set mostly by round trips and payload size, not by raw bandwidth.
  2. Networks are built in layers. You work at the application layer (HTTP, WebSocket), but TCP, TLS, IP and DNS decide how fast it feels.
  3. A page load is a chain: DNS, then TCP, then TLS, then HTTP. Caches and CDNs exist to skip links in that chain.
  4. To fetch data you choose between REST, GraphQL and gRPC. To get live updates you choose between polling, SSE and WebSocket. Each choice is a trade-off, not a ranking.
  5. A production client assumes the network fails: timeouts, cancellation, retries with backoff and jitter, and graceful degradation.

Core concepts

Why networking matters in frontend system design

This topic explains how networking shows up in interviews and defines the words you will use in every later answer. Without exact vocabulary, trade-off arguments stay vague.

How networking questions appear in interviews

Interviewers rarely ask you to recite what TCP stands for. They ask a design question, such as "how does the feed update live?", and listen for the networking decisions inside your answer. They look for four things: you name the data flow, you choose a protocol and say why, you estimate cost in round trips and bytes, and you say what happens when the network fails. shows that sequence as a checklist you can run on any question.

Read the figure left to right. Each box is something to say out loud; skipping "Estimate" or "Handle failure" is the most common reason an answer sounds shallow.

The vocabulary: latency, bandwidth, throughput, round trips, payload size

Latency is how long one message takes to arrive. Bandwidth is how much the link could carry per second. Throughput is what you really get, which is lower because of loss, congestion and protocol overhead. A round trip is a request plus its response, so one round trip costs one RTT. Payload size is the number of bytes you send. Why it matters: loading a small file is limited by RTT, while loading a large file is limited by throughput. Most API calls are small, so they are RTT-bound. In , the browser is idle for a whole RTT after each request.

Two requests in sequence cost two RTTs plus two processing times, even on a fast link. That is why batching, caching and keeping connections open often help more than a faster connection. The script below turns this into numbers.

For small requests, cut round trips. For large responses, cut bytes. Buying more bandwidth helps only the second case.

Network layers

Layering is how the network is organised so that each part can change without breaking the others. Knowing which protocol lives on which layer lets you place any problem, from a DNS failure to a slow handshake, on the right layer.

Why layering exists

A network has too many jobs for one component: moving bits, finding routes, retransmitting lost data, encrypting, and formatting messages. Layering splits these jobs. Each layer does one thing and serves only the layer above it, hiding how it works. This is separation of concerns, and the design pattern is Layered architecture. The payoff: HTTP does not care whether the bits travel over Wi-Fi or Ethernet, so a phone can switch networks without any change in your fetch code. shows the dependency direction.

Replace the bottom box and nothing above it changes. That is the whole argument for layers.

The OSI model and the TCP/IP model, side by side

Two models describe the layers. OSI has seven layers and is the teaching vocabulary: engineers say "layer 7" and "layer 4". TCP/IP has four layers and describes what the internet actually runs. They describe the same stack with different groupings, as shows.

TCP/IP merges OSI layers 5 to 7 into one Application layer, and layers 1 and 2 into one Link layer. Transport and Network (called Internet in TCP/IP) line up one to one.

Each layer explained simply

lists what each OSI layer does, the unit of data it handles, how it addresses things, and example protocols. Read it top to bottom as the path an outgoing request takes.

In plain words:

  • Application: what the two programs say to each other, such as an HTTP request.
  • Presentation: how that message is encoded and protected, such as UTF-8 text or TLS encryption.
  • Session: keeping a conversation open and recoverable. In practice, few stacks have a separate session layer.
  • Transport: getting data to the right program on the other machine, using a port number.
  • Network: finding a path across many networks, using an IP address.
  • Data link: moving a frame to the next device on the same link, using a MAC address.
  • Physical: turning bits into electrical, optical or radio signals.

TLS is placed differently in the two models. OSI puts encryption at the presentation layer. TCP/IP has no such layer, so TLS is treated as part of the application layer, running on top of TCP. HTTP/3 goes further: QUIC builds TLS 1.3 into the transport itself.

Encapsulation and decapsulation

To send an HTTP request, each layer wraps what it receives from above inside its own header. This is encapsulation. The receiver does the reverse, unwrapping one header per layer: decapsulation. Each header holds only what that layer needs: ports for the transport layer, IP addresses for the network layer, MAC addresses for the link layer. shows the sending side.

The server reads the diagram bottom to top. The link layer checks the MAC address, the network layer checks the IP address, the transport layer uses the port to pick the right process, and the application finally sees the original HTTP text. With HTTPS, TLS encrypts the HTTP message before it becomes the TCP payload. The script below builds and unwraps these layers.

TCP vs UDP in detail, and where QUIC fits

TCP first sets up a connection with a handshake, then delivers a reliable, ordered stream of bytes. It numbers bytes, acknowledges them and retransmits losses. Flow control stops a fast sender from overwhelming a slow receiver. Congestion control slows the sender when the network is overloaded. The price is extra round trips at the start, and head-of-line blocking: one lost segment delays everything behind it. UDP sends independent datagrams with no connection, no ordering and no retransmission. It is fast and simple, and the application decides what to do about loss. contrasts the two.

TCP spends effort to hide the network's flaws; UDP exposes them. QUIC is a newer transport built on top of UDP. It adds reliability, ordering per stream, congestion control and TLS 1.3, and it removes TCP's cross-stream head-of-line blocking. HTTP/3 runs on QUIC. Use to choose.

Start at the top question. Most web traffic ends at TCP or QUIC; UDP is chosen when a late packet is worse than a missing one. Run the script below to see both transports exchange the same message.

Which device works at which layer

A device is defined by the deepest header it reads. A switch reads MAC addresses (layer 2). A router reads IP addresses (layer 3). A layer 4 load balancer routes by IP and port without reading HTTP. A layer 7 load balancer reads URLs, headers and cookies, so it can route /api and /images to different servers. Proxies, API gateways and CDN edges work at layer 7. Firewalls range from layer 3 and 4 packet filters to layer 7 web application firewalls. follows one request across them.

The frame is rebuilt at every hop (new MAC addresses), while the IP packet inside keeps its source and destination addresses end to end.

Ports and sockets

An IP address finds a machine; a port (0 to 65535) finds a program on it. A socket is one end of a conversation, and a connection is identified by four values: source IP, source port, destination IP and destination port. The server keeps listening on one well-known port, while each client connection uses a different temporary source port. That is how one server on port 443 serves thousands of clients, and how two browser tabs to the same site stay separate ().

Where a frontend developer's work sits

Your code lives mostly at the application layer: URLs, methods, headers, JSON, WebSocket messages. But the lower layers set the cost of every request. How the web works

This topic follows one page load from a typed URL to the first byte of the response: name lookup, connection, encryption, request. Each step has a cost in round trips, and each step has a trick to skip it.

The client-server model and the anatomy of a URL

The web uses the client-server pattern: a client (your browser) starts a request and a server answers it. The server never contacts the client first. A URL tells the client everything it needs to start: which protocol to speak, which machine to find, which program on that machine, and which resource to ask for. breaks one URL into its parts.

The scheme chooses the protocol and the default port. The host is resolved with DNS. The path and query go into the HTTP request line. The fragment stays in the browser, which uses it to scroll or to route inside a single-page app.

DNS resolution

Computers route by IP address, but people use names. DNS is the distributed lookup service that turns shop.example.com into an address. A recursive resolver (run by your ISP or a public service) does the work for you: it asks a root server, then the top-level-domain (TLD) server for com, then the authoritative server that owns example.com. Answers carry a TTL (time to live) that says how long they may be cached. shows an uncached lookup.

Most lookups never reach the root: the browser cache, the operating system cache, the home router and the resolver each remember recent answers until the TTL expires. A cold lookup costs several round trips; a cached one costs none. DNS usually runs over UDP on port 53. The script below asks the operating system's resolver for an address.

The TCP three-way handshake

Before sending data, TCP makes both sides agree on starting sequence numbers. The client sends SYN, the server replies SYN-ACK, and the client confirms with ACK. The client may send data right after its ACK, so the handshake costs one round trip before the first byte of the request ().

This is why keep-alive (reusing one connection for many requests) matters: it pays the handshake once. The script below measures a handshake against a local server; point it at a remote host to see a real round trip.

The TLS handshake and HTTPS

HTTPS is HTTP carried inside TLS. TLS gives three guarantees: privacy (encryption), integrity (tampering is detected) and authentication (the server proves its identity with a certificate signed by a trusted authority). In TLS 1.3 the handshake takes one round trip after TCP; TLS 1.2 needed two. shows the TLS 1.3 exchange.

After the client checks the certificate, both sides share keys and everything that follows is encrypted. A returning client can resume a session and, with 0-RTT, send data in the first flight, though 0-RTT data can be replayed by an attacker, so servers should only accept safe requests that way. The perf-timing.js snippet from section 1.2.8 shows the TLS time of a real page load.

Follow the arrows from the top. A fresh cache entry ends the journey at step 1. Otherwise the browser resolves the name, opens TCP, then TLS, then sends the request, and any of these steps may be shortened by a cached DNS answer, a reused connection or a CDN hit.

CDNs and edge caching

A CDN (content delivery network) is a set of servers spread around the world. Users connect to the nearest edge server, which answers from its cache if it can and fetches from the origin only on a miss. This cuts round-trip time (the server is close), cuts load on the origin, and absorbs traffic spikes. The origin controls what may be cached through Cache-Control headers ().

The first user in a region pays for the miss; everyone after gets the hit. Static, fingerprinted files cache best. The snippet below reads response headers that CDNs commonly add (header names differ per provider, VERIFY for yours). 

// Run in the browser console on a site that uses a CDN.
const res = await fetch('/logo.png');
console.log({
  age: res.headers.get('age'),                   // seconds the object has been in a shared cache
  cacheControl: res.headers.get('cache-control'), // the origin's caching rules
  cdnStatus: res.headers.get('x-cache') ?? res.headers.get('cf-cache-status'), // HIT or MISS (provider specific)
});

When asked "what happens when you type a URL", answer in layers and name the cache shortcut at each step. It shows you know the cost of each step, not just the order.

HTTP in depth

HTTP is the language your frontend speaks every day. This topic covers its message format, its caching rules, its security-related headers and how its versions differ.

Request and response anatomy

An HTTP message is plain text: a start line, headers, a blank line and an optional body. A request starts with a method and a path; a response starts with a status code. HTTP is stateless: each request carries everything the server needs, which is why cookies and tokens exist. shows one exchange.

The request line has three parts (method, path, version). The response line has the version, the status code and a reason phrase. The script below sends a raw request over a TCP socket and prints the raw reply.

Methods: safe and idempotent

A method says what you want to do. A safe method does not change server state (GET, HEAD, OPTIONS). An idempotent method has the same effect whether you send it once or ten times (GET, PUT, DELETE). POST is neither, and PATCH is not guaranteed to be idempotent. Idempotency decides whether a failed request can be retried automatically, as shows.

Safe methods are also idempotent, but not the other way round: DELETE changes state, yet deleting twice leaves the same end state.

A classic trap: fetch only rejects on network failure, not on 4xx or 5xx. Check res.ok yourself. 

async function getJson(url) {
  const res = await fetch(url);
  if (!res.ok) throw new Error(`HTTP ${res.status}`); // fetch resolves even for 404 and 500
  return res.status === 204 ? null : res.json();      // 204 has no body to parse
}

Important headers

Headers carry metadata so the body can stay simple. Request headers describe the client and what it wants; response headers describe the body and how to handle it. groups the ones you need most.

The top arrow is what the client says; the bottom arrow is what the server answers. Content-Type tells the browser how to read the body, Location drives redirects, and Access-Control-* headers drive CORS.

Content negotiation and compression

With content negotiation the client lists what it can handle and the server picks one: Accept for format, Accept-Language for language, Accept-Encoding for compression. The server states its choice in Content-Type, Content-Language and Content-Encoding, and adds Vary so caches store one copy per variation (). Compression trades a little CPU for far fewer bytes on text.

The browser decompresses transparently, so your code never sees the encoding. Brotli (br) usually compresses text better than gzip. Already-compressed files such as JPEG and WOFF2 should not be compressed again.

HTTP caching

The fastest request is the one never sent. The Cache-Control header tells browsers and shared caches whether to store a response and for how long. When a stored copy is stale, the browser can revalidate it with a conditional request (If-None-Match with the ETag, or If-Modified-Since with Last-Modified), and the server answers 304 Not Modified with no body if nothing changed. shows the decision a browser makes.

Start at the top. A fresh copy costs nothing. A stale copy with a validator costs one small round trip. Only a missing copy costs a full download. stale-while-revalidate goes further: the browser shows the stale copy immediately and refreshes it in the background.

Using no-cache when you mean no-store. no-cache still stores the response; it only forces revalidation. For private data that must never be written to a cache, use no-store.

Cookies and authorization headers

Because HTTP is stateless, the server needs a way to recognise a returning user. A cookie is set by the server with Set-Cookie and then sent back by the browser automatically on matching requests. A token in the Authorization header is added by your code on each request. Cookies are sent automatically (convenient, but they need CSRF protection); header tokens are sent only when your code adds them. Full security is covered in a later chapter. shows both.

The cookie flags matter: HttpOnly hides it from JavaScript, Secure sends it only over HTTPS, and SameSite limits cross-site sending. 

// Server (Express): the session cookie cannot be read by scripts and is HTTPS-only.
res.cookie('sid', sessionId, { httpOnly: true, secure: true, sameSite: 'lax', maxAge: 60 * 60 * 1000 });

// Client: cookies on cross-origin calls need credentials: 'include' (and matching CORS headers).
fetch('https://api.example.com/me', { credentials: 'include' });

// Client: a bearer token is added explicitly.
fetch('/api/data', { headers: { Authorization: `Bearer ${accessToken}` } });

CORS and preflight requests

Browsers apply the same-origin policy: a page may not read responses from another origin (a different scheme, host or port) unless that server opts in with CORS headers. Simple requests (for example a GET with safe headers) are sent directly, and the browser checks the response headers. Anything else (a PUT, DELETE, JSON Content-Type or an Authorization header) first triggers a preflight: an automatic OPTIONS request asking whether the real request is allowed. Preflight exists to protect older servers that never expected such requests from a web page ().

The preflight answer can be cached with Access-Control-Max-Age, which saves a round trip; browsers cap the value (Chromium at 2 hours, Firefox at 24 hours). CORS is enforced by the browser, not the server: curl and other servers ignore it, so it is not an authentication mechanism.

HTTP/1.1, HTTP/2 and HTTP/3

HTTP/1.1 sends one request at a time per connection, so browsers open about six connections per host and a slow response blocks the ones behind it (head-of-line blocking at the HTTP level). HTTP/2 adds multiplexing: many streams share one TCP connection as interleaved frames, plus header compression. But one lost TCP segment still stalls all streams. HTTP/3 runs on QUIC over UDP, so streams recover from loss independently, and it connects faster by merging the transport and TLS handshakes. compares them.

Reading left to right, each version removes one waiting point. A practical consequence: HTTP/1.1-era tricks (domain sharding, giant sprite sheets, bundling everything) can hurt under HTTP/2 and HTTP/3. Use the snippet to see which version your pages use. 

// Run in the browser console: 'http/1.1', 'h2' (HTTP/2) or 'h3' (HTTP/3) for each request.
performance.getEntriesByType('resource').forEach((r) => console.log(r.nextHopProtocol, r.name));

Communication protocols for real-time updates

Plain HTTP only lets the client ask. This topic covers five ways to get fresh data to the screen, from repeated asking to a permanent two-way channel, and the engineering needed to keep them alive.

Short polling

The client asks the server for updates on a timer, for example every 5 seconds. It is the simplest technique: plain HTTP, works everywhere, easy to cache and debug. The cost is waste and delay. Most answers say "nothing new", and a change can wait up to one full interval before the user sees it ().

Every loop pays a full request, including headers, even when nothing changed. Use it when updates are rare, a few seconds of delay is fine and simplicity matters most. 

// The simplest possible poller. Pause it when the tab is hidden to save requests.
async function poll() {
  if (document.hidden) return;
  const res = await fetch('/api/status');
  render(await res.json());
}
setInterval(poll, 5000);

Long polling

In long polling the server holds the request open until it has something to say, or until a timeout (often 20 to 60 seconds). The client then immediately sends the next request. Updates arrive almost instantly, and the server sends nothing when nothing changes. The cost is one open connection per client and a new request after every message ().

The version number in the request lets the server answer at once if the client missed something while reconnecting. The script below runs both techniques against a local server that changes every 1.5 seconds.

Server-Sent Events (SSE)

SSE keeps one HTTP response open and streams text events from the server to the browser. It is one-way (server to client), uses plain HTTP, and the browser's EventSource API reconnects automatically and sends Last-Event-ID so the server can resume. This is the Observer / Pub-Sub pattern: clients subscribe to a stream and the server publishes events to every subscriber ().

Limits: text only, server to client only, and over HTTP/1.1 browsers allow about six connections per domain across all tabs, so several SSE streams can starve other requests (HTTP/2 raises this, with 100 streams as a common default). Cookies and headers work normally, but the native EventSource cannot set custom headers.

WebSockets

A WebSocket starts as an HTTP request with an Upgrade header; if the server agrees (status 101), the same TCP connection switches to a full-duplex message protocol. Both sides can send at any time, with very small frame overhead. It suits chat, games, collaborative editing and trading screens ().

Unlike HTTP, a WebSocket is stateful: the server must remember every open connection, and you must write your own reconnect, heartbeat and message-format logic. Its lifecycle is shown in .

The browser reports these as readyState values 0 (connecting), 1 (open), 2 (closing) and 3 (closed). The last arrow is not built in: reconnecting is your job. Share one socket for the whole app instead of one per component. That is the Singleton pattern, applied to a connection.

WebRTC

WebRTC connects two browsers directly (peer to peer) for audio, video and arbitrary data, usually over UDP. It needs a signaling channel (often a WebSocket) to exchange connection offers, and STUN/TURN servers to find a path through home routers (NAT): STUN discovers your public address, and TURN relays traffic when a direct path is impossible. It is built for low latency and tolerates packet loss, which is why video calls use it. It is heavy for simple data pushing ().

The signaling server only introduces the peers; once connected, the media bypasses it. Use WebRTC for calls and peer-to-peer data; use a WebSocket for ordinary client-to-server messaging. 

// Browser: create a data channel and an offer. Sending the offer through your signaling channel is left out.
const pc = new RTCPeerConnection({ iceServers: [{ urls: 'stun:stun.l.google.com:19302' }] });
const channel = pc.createDataChannel('chat');
channel.onopen = () => channel.send('hello peer');
channel.onmessage = (e) => console.log('peer says:', e.data);
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);   // then send `offer` to the other peer through signaling

Reconnection, heartbeats, backoff with jitter, ordering and delivery guarantees

Long-lived connections will drop: phones switch networks, laptops sleep, proxies close idle sockets. A heartbeat (a small ping and pong at a fixed interval) detects a dead connection that the OS has not noticed. After a drop, retry with exponential backoff (wait longer after each failure) and jitter (randomise the wait). Without jitter, thousands of clients reconnect at the same instant after a server restart and knock it over again. This is the Retry with backoff pattern ().

The resume step is what makes the loop correct. Give every server message an increasing sequence number; the client remembers the last one it processed and asks for everything after it. Delivery guarantees follow: at-most-once (may lose messages), at-least-once (may duplicate, so the client must ignore duplicates), and "exactly-once" in practice, which is at-least-once plus idempotent handling. The ws-client.js file above implements the loop and heartbeat; the snippet below adds duplicate and gap handling. 

let lastSeq = 0;
function handle(msg) {
  if (msg.seq <= lastSeq) return;                  // duplicate or replay: ignore (idempotent handling)
  if (msg.seq !== lastSeq + 1) requestReplay(lastSeq); // gap detected: ask the server for what was missed
  lastSeq = msg.seq;
  render(msg);
}

Scaling concerns at a high level

Real-time connections are long-lived, so capacity is counted in open connections, not requests per second. Each one uses memory and a file descriptor on the server. When you run several socket servers, a message received by server 1 must also reach clients connected to server 2. The usual answer is a Pub/Sub broker (such as Redis or a message queue): each server publishes incoming messages and subscribes to messages for its own clients. This is fan-out ().

Without the broker, users on different servers could not talk to each other. Sticky sessions (the load balancer keeps a client on one server) are needed only by libraries that fall back to polling. Also plan for rolling deploys: closing a server drops thousands of sockets at once, which is where jittered reconnects pay off.

Opening one WebSocket or EventSource per component. Ten widgets become ten connections, and over HTTP/1.1 the browser's six-connection limit can block ordinary requests. Share one connection and fan out events inside the app.

REST APIs

REST is the default style for web APIs: resources named by URLs, acted on with HTTP methods. This topic covers how to design the URLs, pages, filters and versions well, and where REST falls short.

Resource modeling and URL design

REST models the system as resources (nouns) such as users and posts, each with a stable URL. Methods supply the verbs. Collections are plural (/users), one item is addressed by id (/users/42), and relationships are nested only one level deep (/users/42/posts). Avoid verbs in paths such as /getUser. shows a resource map.

Once a post has its own top-level URL (/posts/9), clients do not need to know its owner to fetch it. This keeps URLs short and stable.

Methods and status codes in practice

Map actions to methods consistently: GET reads, POST creates, PUT replaces, PATCH changes part, DELETE removes. Return the status that matches the outcome: 201 Created with a Location header for a new resource, 204 when there is nothing to return, 404 for a missing resource, 422 for validation errors. Clients then need no guessing ().

Each reply tells the client what to do next without reading the body: store the new URL, show the update, remove the row.

Idempotency

Networks fail between the server finishing the work and the client receiving the answer, so clients retry. For PUT and DELETE that is harmless. For POST it creates a duplicate order or a double charge. The fix is an idempotency key: the client generates a unique key per user action and sends it in a header; the server stores the first result under that key and returns it for any repeat ().

Generate the key when the user clicks, not when the request is sent, so every automatic retry reuses it. The script compares plain POST, PUT and POST with a key.

Pagination: offset and cursor

Never return an unbounded list. Offset pagination (?offset=20&limit=10) is easy and allows jumping to page N, but the database must skip rows (slow for deep pages) and the pages shift if items are inserted or removed while the user browses. Cursor pagination (?after=abc&limit=10) asks for "items after this one": it stays fast and stable, but you cannot jump to an arbitrary page. Infinite scroll and feeds should use cursors ().

The cursor is a bookmark, so it does not care how many rows were inserted before it. The server returns nextCursor, and the client keeps following it until it is null.

Filtering, sorting and versioning

Express filters, sorting and page size as query parameters on the collection: /posts?status=published&sort=-createdAt&limit=20. Validate and whitelist them on the server. Versioning lets you change the API without breaking old clients. The common choices are a path prefix (/v1/posts, simple and visible), a header or media type (cleaner URLs, harder to test in a browser), or no explicit version with only additive changes (new fields are fine, removals are not). shows how one URL is read.

A leading minus sign for descending order is a common convention, not a standard, so document whichever style your API uses. Build query strings with URLSearchParams so values are encoded correctly. 

const params = new URLSearchParams({ status: 'published', sort: '-createdAt', limit: '20' });
const res = await fetch(`/api/v1/posts?${params}`); // encodes special characters for you

Over-fetching and under-fetching

Over-fetching means a response carries more fields than the screen needs, which wastes bytes on mobile networks. Under-fetching means one endpoint is not enough, so the client chains several requests (a user, then their posts, then each post's comments) and pays a round trip for each. Both come from fixed server-defined response shapes (). They are the main reason GraphQL and backend-for-frontend layers exist.

Mitigations inside REST: sparse fieldsets (?fields=id,name), an ?include=posts parameter, or an endpoint shaped for one screen.

HATEOAS (briefly)

HATEOAS (hypermedia as the engine of application state) means responses include links to the actions available next, so the client follows links instead of building URLs. It is the top level of strict REST, but most public APIs skip it and publish documentation instead. It is useful for workflows where the allowed actions depend on state, such as an order that can be paid or cancelled ().

The client never hard-codes the payment URL; if the order were already paid, the server would simply omit the pay link. 

{
  "id": 7,
  "status": "pending",
  "links": {
    "self":   { "href": "/orders/7", "method": "GET" },
    "pay":    { "href": "/orders/7/payment", "method": "POST" },
    "cancel": { "href": "/orders/7", "method": "DELETE" }

GraphQL

GraphQL lets the client describe exactly the data it needs in one request. This topic explains its building blocks, what it fixes, and the costs that come with it.

Schema, queries, mutations and subscriptions

A GraphQL server publishes a typed schema: the contract of every type and field. Clients send one of three operations. A query reads data. A mutation writes data. A subscription receives pushed events, usually over a WebSocket (). Because the schema is typed and introspectable, tools can validate queries and generate client types before the code runs.

Queries and mutations travel over ordinary HTTP; only subscriptions need a persistent connection. The schema below declares one of each.

Solving over-fetching and under-fetching

The client names the fields it wants, so the response has exactly those fields (no over-fetching), and related data can be requested in the same query (no chain of calls, so no under-fetching). On slow mobile networks, one round trip instead of three is a clear win. compares the two flows for the same screen.

The saving is real when round trips dominate. If your REST endpoints are already shaped for the screens, the gain is smaller.

The costs: caching, complexity, N+1 and persisted queries

GraphQL moves work to the server and removes some of HTTP's free features.

  • Caching: every request is a POST to one URL, so browsers and CDNs cannot cache by URL. Clients keep a normalised cache by object id instead; persisted queries (send a hash, not the text) allow GET and CDN caching.
  • Query complexity: a client can ask for deeply nested data. Servers limit query depth and cost, and time out expensive queries.
  • The N+1 problem: resolving a list of 20 posts and each author can cause 1 query for the posts plus 20 for the authors. A batching layer (the DataLoader pattern) collects the 20 author lookups into one.
  • Errors: a response can be HTTP 200 and still contain an errors array, so monitoring must look inside the body.

How a frontend client talks to GraphQL

The client sends one POST to a single endpoint (commonly /graphql) with a JSON body holding a query string and a variables object. Variables keep the query text constant, which helps caching and avoids string building. Fragments let components declare the fields they need and share them. Libraries such as Apollo Client or urql add caching and hooks, but the wire format is just HTTP and JSON ().

gRPC

gRPC is a fast, strictly typed way for services to call each other. This topic explains how it works, why browsers cannot use it directly, and where it belongs in a frontend architecture.

Protocol Buffers and HTTP/2 transport

You describe the API in a .proto file: messages (data shapes) and services (callable methods). A compiler generates typed client and server code in many languages. Messages travel as compact Protocol Buffers binary over HTTP/2, so they are smaller and faster to parse than JSON, and HTTP/2 gives multiplexing and streaming (). The cost is that binary payloads are not human-readable in DevTools.

Both sides compile from the same file, so a field renamed on one side is a compile error on the other. Field numbers (not names) identify data on the wire, so you can add fields without breaking old clients.

The four call types

gRPC has four shapes of call. Unary: one request, one response, like a normal function call. Server streaming: one request, a stream of responses (a live feed). Client streaming: a stream of requests, one response (uploading chunks). Bidirectional streaming: both sides stream independently (chat). shows each.

The first two are the ones web apps need most. Calls 3 and 4 need full control over HTTP/2 streams, which browsers do not give you (see the next section).

gRPC-Web and why browsers cannot call gRPC directly

gRPC relies on HTTP/2 features that browser APIs do not expose: fine control over frames, and trailers (headers sent after the body, where gRPC puts its final status). fetch and XHR hide these details. gRPC-Web is a variant that fits inside what browsers can do: the status is encoded in the body, and a proxy (commonly Envoy, or a server with built-in support) translates between gRPC-Web and real gRPC. It supports unary and server-streaming calls; client and bidirectional streaming are not available from the browser ().

Every extra hop adds operations work, which is a main reason frontends often call REST or GraphQL while services call each other with gRPC. Alternatives that work in browsers without a translating proxy, such as the Connect protocol, exist; check current support before choosing (VERIFY).

The one-line answer to "why can't browsers call gRPC": the browser APIs do not expose HTTP/2 frames or trailers, which gRPC needs, so gRPC-Web plus a proxy is required.

Where gRPC fits and where it does not

gRPC shines between backend services: strict contracts, small payloads, low latency, streaming, code generation in many languages. It fits poorly on the public edge: browsers need a proxy, payloads are not easy to inspect, and public developers expect REST. The common design uses REST or GraphQL to the browser, and gRPC behind a gateway or BFF ().

The frontend team sees one friendly API; the backend teams keep their efficient internal protocol. The gateway is the translation point.

Choosing the right approach

Knowing each technology is half the skill; choosing between them is the interview. This topic gives decision flows for data APIs and for live updates, and the architecture that connects frontends to many services.

REST, GraphQL or gRPC

Choose by who calls whom and what hurts most. Public or simple CRUD APIs with HTTP caching: REST. Many different clients and screens with varied data needs, or deep relationships: GraphQL. Service-to-service calls where speed and contracts matter: gRPC. turns this into questions. The full comparison table is in the Trade-offs part of this chapter.

Notice that the first question is about the caller, not the technology. These styles also combine: a REST API for the public, GraphQL for your own apps and gRPC inside.

Polling, SSE or WebSocket

For live updates, ask which direction data flows and how fast it changes. Updates that are rare and tolerate a delay: polling. Server-to-client only (notifications, tickers, progress): SSE. Frequent messages in both directions (chat, collaboration, games): WebSocket. shows the path.

SSE is the underused answer: it covers a large share of "live" features with less infrastructure than WebSockets. Reach for WebSocket when you truly need two-way traffic.

Backend-for-Frontend (BFF) and the API gateway

An API gateway is a single entry point in front of many services. It handles shared concerns: routing, authentication, rate limiting, TLS. A Backend-for-Frontend is a small server owned by one frontend (web, iOS, Android). It calls the internal services and returns exactly what that client's screens need. The BFF is a Facade (one simple interface over many services) and an Adapter (it translates internal shapes into UI shapes). Because the frontend team owns it, they can change it without waiting for several backend teams ().

Without a BFF, each client makes many calls and reshapes data itself. The cost is one more service to run and keep consistent. The script below merges two services into one response.

Frontend network resilience and efficiency

Networks are slow, flaky and sometimes absent. This topic covers the habits that keep an app usable anyway: bounded waiting, careful retries, fewer duplicate requests and honest behaviour offline.

Timeouts and request cancellation

fetch has no default timeout, so a stalled request can wait for minutes. Always set a limit, and cancel work the user no longer needs, such as the previous search when they type again or a request for a screen they left. Use an AbortController: abort() makes the fetch promise reject, and the browser stops the request ().

Whichever path ends the request, clean up the timer. Handle the abort error separately from real failures so a cancelled request does not show an error to the user. 

// React: cancel the request when the component unmounts or the id changes (avoids stale results).
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/users/${id}`, { signal: controller.signal })
    .then((res) => res.json())
    .then(setUser)
    .catch((err) => { if (err.name !== 'AbortError') setError(err); });
  return () => controller.abort();
}, [id]);

Retries with exponential backoff and jitter

Many failures are temporary, so retrying helps, but retrying badly makes outages worse. Retry only failures that can be transient (network errors, 429, 5xx) and only for requests that are safe to repeat. Wait base x 2^attempt up to a cap, and add jitter. Stop after a few attempts and show an error ().

The loop in the figure is exactly what the code does: the retry condition is the diamond, the wait is the random delay. If the server sends a Retry-After header, use it instead of your own delay.

Request deduplication, batching, debounce and throttle

The cheapest request is one you never send. Deduplication: if three components ask for the same URL at the same time, send one request and share the promise. Batching: combine many small requests (for example 20 ids) into one call. Debounce: wait until the user stops typing before calling. Throttle: allow at most one call per interval, for scroll or resize (). Libraries such as TanStack Query and SWR do this for you.

Handling 429 and 5xx responses

A 429 Too Many Requests means you are over a rate limit: wait for the time in Retry-After (seconds or a date), do not hammer. A 5xx means the server failed, which is often temporary: retry idempotent requests with backoff, and for POST only with an idempotency key. A 4xx other than 429 means the request itself is wrong, so retrying cannot help ().

The 401 branch deserves care: refresh the token once and share that refresh between concurrent requests, otherwise ten failing calls start ten refreshes. The helper below reads Retry-After in both of its forms. 

// Retry-After is either a number of seconds or an HTTP date.
function retryAfterMs(res) {
  const v = res.headers.get('Retry-After');
  if (!v) return null;
  const seconds = Number(v);
  return Number.isFinite(seconds) ? seconds * 1000 : Math.max(0, Date.parse(v) - Date.now());
}

Offline detection and graceful degradation

navigator.onLine and the online and offline events tell you when the device has no network at all, but a "true" value does not prove the server is reachable. Treat failed requests as the real signal. Degrade gracefully: show cached data with a notice, queue user actions (such as sending a message) and replay them when the connection returns, and disable features that cannot work. shows the states.

The Syncing state matters: do not jump straight from offline to online, because queued actions must be sent first, in order, and may fail. 

const queue = [];                       // actions the user made while offline
function send(action) {
  if (!navigator.onLine) { queue.push(action); showBanner('Offline: will send when you reconnect'); return; }
  return post(action);
}
window.addEventListener('online', async () => {
  while (queue.length) await post(queue.shift()); // replay in order
  hideBanner();
});

An API client layer (added topic)

Instead of calling fetch in every component, put timeouts, auth headers, retries, error mapping and data reshaping in one module. This is a Facade (one simple interface over several concerns) and an Adapter (it converts the server's shape, such as first_name, into the UI's shape, such as displayName). When the API changes, you change one file ().

Components never see HTTP details. The same layer is also where you add logging, request ids and a global handler for expired sessions.

Protocol-choice workshop

Six realistic scenarios put the whole chapter to work. For each one, state the recommended approach, why it wins, and what you would watch out for. Practise saying these aloud.

Chat application

Recommended: WebSocket (history over REST). Messages flow both ways, often and with low delay, so a persistent two-way channel fits. Load old messages with cursor pagination, send new ones over the socket, and add heartbeat, reconnect with resume by sequence number, and an idempotency id per message to avoid duplicates. Scale with a Pub/Sub broker behind several socket servers ().

The acknowledgement with a sequence number lets Alice mark the message as sent, and lets either client detect a gap after reconnecting.

Stock ticker

Recommended: SSE or WebSocket, with server-side throttling. Prices flow from server to client only, so SSE is enough and simpler. Choose WebSocket if the user also sends subscriptions at high frequency or you need binary data. Do not render every tick: the server (or client) should coalesce updates to the latest price every 100 to 250 ms, since the eye cannot read faster (). Decide what happens on reconnect: usually send a fresh snapshot, not the missed ticks.

Coalescing protects both the network and the main thread. On reconnect, a snapshot is correct and cheap, because old prices are worthless.

Notification bell

Recommended: SSE (fallback: long polling or polling every 30 to 60 seconds). Notifications are rare, text-only and server-to-client, which is what SSE is for. Fetch the unread count over REST on load, then let SSE push increments. For notifications when the tab is closed, use the Push API with a service worker, which is a different mechanism ().

Starting from a REST snapshot means a dropped SSE stream never leaves the count wrong for long: reconnect and refetch.

News feed

Recommended: REST or GraphQL with cursor pagination, plus a light "new posts" check. A feed is read-heavy and cacheable. Load pages by cursor for infinite scroll, cache the first page at the CDN or client, and poll cheaply (or use SSE) for a "new posts available" signal instead of inserting items under the user's eyes. Prefetch the next page when the user nears the end ().

Real-time insertion is avoided on purpose: content that jumps while someone reads is a worse experience than a one-tap refresh.

File upload

Recommended: direct upload to object storage with a pre-signed URL, in resumable chunks for large files. Sending big files through your application server wastes its bandwidth and memory. The client asks your API for a signed URL, then uploads straight to storage. For files above a few megabytes, split into chunks so a dropped connection resumes instead of restarting. For progress bars, XMLHttpRequest exposes upload progress events; fetch does not (streaming uploads with fetch are only partly supported, VERIFY) ().

The API server only handles small metadata calls, and each chunk is idempotent, so retrying a failed chunk is safe.

Collaborative editor

Recommended: WebSocket carrying operations, with a conflict-resolution algorithm (OT or CRDT). Many users edit the same document, so changes must flow quickly in both directions, and concurrent edits must merge without losing anyone's work. Send small operations, not whole documents, apply local edits immediately (optimistic updates) and reconcile with the server's order. Show presence (cursors) over the same channel and keep an offline queue (). The algorithms themselves are beyond this chapter.

Local application keeps typing instant; the server's merge keeps every copy convergent. This is the Pub/Sub pattern with an ordering step in the middle.

Common mistakes

  • Treating bandwidth as the cure for slowness. Most API calls are small. Count round trips and cut them first.
  • Assuming fetch rejects on 404 or 500. It only rejects on network failure. Check res.ok.
  • No timeout and no cancellation. A stalled request hangs the UI, and stale responses overwrite fresh ones.
  • Retrying everything immediately. Retry only transient errors, only safe requests, with backoff and jitter.
  • Confusing no-cache with no-store. no-cache still stores and revalidates.
  • Treating CORS as security for your API. The browser enforces it; other clients ignore it. Authenticate on the server.
  • Reflecting any Origin with credentials allowed. Use an explicit allow-list.
  • Polling when SSE would do, or WebSocket when SSE would do. Pick the lightest tool that meets the direction and rate.
  • One socket per component. Share one connection and fan out events in the app.
  • Reconnecting without jitter or resume. You get thundering herds and lost or duplicated messages.
  • Offset pagination on a live feed. Items repeat or vanish as data changes. Use cursors.
  • Using the HTTP/1.1 playbook everywhere. Domain sharding and mega-bundles can hurt on HTTP/2 and HTTP/3.
  • Ignoring GraphQL's error shape. A 200 response can carry errors; monitor the body.

Most-asked interview questions

Ordered from basic to advanced. Each answer is built to be spoken in about two minutes: lead with the short answer, then give structure.

Q1. What is the difference between the OSI model and the TCP/IP model?

Short answer. Both describe how network communication is layered. OSI has seven layers and is a reference vocabulary. TCP/IP has four layers and describes what the internet actually runs.

  • OSI: Application, Presentation, Session, Transport, Network, Data link, Physical.
  • TCP/IP: Application, Transport, Internet, Link.
  • Mapping: TCP/IP Application covers OSI 5 to 7. Transport matches Transport. Internet matches Network. Link covers OSI 1 and 2.

Why it matters. Engineers use OSI numbers as shorthand ("a layer 7 load balancer"), while real protocols such as HTTP, TLS and QUIC do not fit the OSI boxes cleanly. TLS is a good example: OSI places it near the presentation layer, TCP/IP treats it as part of the application layer on top of TCP.

Q2. Which layer do HTTP, TCP, IP and DNS belong to?

Short answer. HTTP and DNS are application layer (layer 7). TCP is transport (layer 4). IP is network (layer 3).

  • HTTP defines requests and responses between a browser and a server.
  • DNS is an application protocol that translates names to IP addresses. It usually runs over UDP port 53, and uses TCP for large answers.
  • TCP delivers a reliable, ordered stream between two programs, identified by ports.
  • IP routes packets between machines, identified by IP addresses.

Follow-up to expect. "Where does HTTPS fit?" HTTPS is HTTP inside TLS, which sits between the application and the transport. "Where does HTTP/3 fit?" It runs over QUIC, which runs over UDP.

Q3. What is encapsulation?

Short answer. Each layer wraps the data from the layer above in its own header (and sometimes a trailer) before passing it down. The receiver removes the wrappers in reverse order, which is decapsulation.

  • Application data (the HTTP request) becomes a TCP segment by adding ports and sequence numbers.
  • The segment becomes an IP packet by adding source and destination IP addresses.
  • The packet becomes an Ethernet or Wi-Fi frame by adding MAC addresses, then goes out as bits.

Why it matters. It explains how a router can forward a packet without understanding HTTP, and why each layer can change independently. Routers rewrite the frame at every hop but keep the IP packet inside.

Q4. TCP vs UDP: when would you use each?

Short answer. TCP is reliable and ordered but pays setup cost and can stall on loss. UDP is connectionless and fast, but the application must handle loss.

  • TCP: handshake, acknowledgements, retransmission, ordering, flow control (do not overwhelm the receiver) and congestion control (do not overwhelm the network). Use for web pages, APIs, email, file transfer.
  • UDP: no handshake, no guarantees. Use for DNS queries, live video and voice, games, where a late packet is useless.
  • QUIC: built on UDP, adds reliable streams and TLS 1.3, and powers HTTP/3. It avoids TCP's head-of-line blocking across streams.

Close with a rule. If correctness matters more than a few milliseconds, choose TCP. If freshness matters more than completeness, consider UDP.

Q5. What is the difference between HTTP and HTTPS?

Short answer. HTTPS is HTTP carried over TLS. The messages are the same, but they are encrypted, tamper-evident and sent to a server whose identity was verified.

  • Privacy: nobody on the path can read the traffic.
  • Integrity: modifications are detected.
  • Authentication: the server proves its identity with a certificate signed by a trusted authority; the browser checks the chain, hostname and expiry.

Cost and how to reduce it. TLS adds a handshake: one extra round trip in TLS 1.3, two in TLS 1.2. Keep-alive, session resumption and HTTP/3 reduce it. Many browser features (service workers, geolocation, secure cookies) require HTTPS, and HTTP pages are marked "not secure".

Q6. What happens when you type a URL into the browser and press Enter?

Short answer. The browser resolves the name, opens a connection, secures it, sends a request, receives a response and renders it. I will cover the network part.

  1. Parse the URL and check the browser cache and service worker. A fresh cached copy ends the journey here.
  2. DNS: look up the IP address, using browser, OS and resolver caches, and the DNS hierarchy on a miss.
  3. TCP handshake (one round trip), or QUIC for HTTP/3.
  4. TLS handshake for HTTPS (one round trip in TLS 1.3).
  5. Send the HTTP request. It may be answered by a CDN edge, otherwise by a load balancer and then the origin server.
  6. Response: the browser starts parsing HTML as bytes arrive and fetches sub-resources, reusing the open connection.

Show depth. Name the layer of each step and the shortcuts: cached DNS, keep-alive, TLS resumption, CDN. Rendering (parse, layout, paint) is a separate topic that I can continue into.

Q7. What is the difference between an L4 and an L7 load balancer?

Short answer. An L4 load balancer routes by IP address and port without reading the content. An L7 load balancer reads the HTTP request and can route by URL, header or cookie.

  • L4: very fast and simple, protocol-agnostic (works for any TCP or UDP service), but it cannot make content-based decisions.
  • L7: can send /api to one pool and /static to another, terminate TLS, add headers, cache, rate-limit and do canary releases. It uses more CPU and must understand the protocol.

Frontend relevance. Long-lived connections such as WebSockets need the balancer to support them and to avoid idle timeouts. Many systems use both: L4 at the outermost edge, L7 behind it.

Q8. How does HTTP caching work?

Short answer. The server labels responses with caching rules. The browser reuses a stored copy while it is fresh, and revalidates it when it is stale.

  • Freshness: Cache-Control: max-age=N says the copy is good for N seconds with no request at all.
  • Validation: once stale, the browser sends If-None-Match with the stored ETag (or If-Modified-Since). If unchanged, the server returns 304 with no body.
  • Who may cache: private (browser only) or public (CDN too). no-store prevents storing.
  • Background refresh: stale-while-revalidate shows the old copy instantly and updates it behind the scenes.

Strategy. Fingerprint static files (app.3f9a1c.js) and cache them for a year with immutable. Serve HTML with short or no freshness and validation, so users pick up new deploys.

Q9. What is CORS, and why does the preflight request exist?

Short answer. Browsers block pages from reading responses from other origins by default (same-origin policy). CORS is the set of headers a server uses to opt in to being read by specific origins.

  • Simple requests (for example GET with safe headers) are sent directly; the browser checks Access-Control-Allow-Origin on the response.
  • Preflighted requests (methods like PUT, JSON content type, custom headers such as Authorization) first send an OPTIONS request with Access-Control-Request-Method and -Headers. The server answers with what is allowed.
  • Why preflight: older servers were built assuming a web page could never send such requests cross-origin. The preflight asks permission before sending anything that could change state.
  • Cost: an extra round trip, reduced by Access-Control-Max-Age (browsers cap it).

Common trap. CORS is not server security: it only controls what a browser lets scripts read. Use credentials with an explicit origin, never *.

Q10. What is idempotency, and why does it matter for retries?

Short answer. An operation is idempotent if doing it several times has the same effect on the server as doing it once.

  • GET, PUT and DELETE are idempotent by definition. POST is not.
  • Why it matters: when a response is lost, the client cannot tell whether the server did the work. A retry of a non-idempotent call can charge twice or create duplicates.
  • The fix for POST: send an Idempotency-Key generated per user action. The server stores the first result under that key and returns it for repeats.

Rule I would state. Automatic retries are safe for idempotent requests, and for others only with an idempotency key. Generate the key when the user clicks, so every retry reuses it.

Q11. HTTP/2 vs HTTP/3: what problem does each solve?

Short answer. HTTP/2 fixes request-level blocking in HTTP/1.1 by multiplexing many streams on one TCP connection. HTTP/3 fixes TCP-level blocking by running over QUIC.

  • HTTP/1.1: one request per connection at a time. Browsers open about six connections per host as a workaround.
  • HTTP/2: multiplexed streams, header compression, one connection. But all streams share one TCP byte stream, so one lost packet stalls them all (TCP head-of-line blocking).
  • HTTP/3: uses QUIC over UDP. Streams are independent, so loss on one does not block the others. It also merges transport and TLS handshakes, so setup is faster, and a connection can survive a network change such as Wi-Fi to mobile.

Practical advice. Enable HTTP/2 and HTTP/3 at your CDN, keep fallbacks, and stop using HTTP/1.1 workarounds such as domain sharding.

Q12. WebSocket vs SSE vs long polling: how do you choose?

Short answer. Choose by direction and frequency of messages, then by infrastructure cost.

  • Long polling: the client asks and the server holds the request until it has data. Works everywhere over plain HTTP, but each message costs a new request. Use as a fallback.
  • SSE: one long-lived HTTP response, server to client, text only. Built-in reconnect and Last-Event-ID. Best for notifications, tickers and progress. Mind the six-connection limit on HTTP/1.1.
  • WebSocket: full-duplex, low overhead, text or binary. Best for chat, collaboration and games. You write reconnect, heartbeat and ordering logic, and servers keep state per connection.

My default. If data flows only from server to client, I start with SSE. I move to WebSocket when the client also sends frequent messages. I use polling only when updates are rare.

Q13. REST vs GraphQL vs gRPC: how do you decide?

Short answer. Pick by the caller and the pain: REST for simple and cacheable public APIs, GraphQL for flexible client-driven data, gRPC for fast service-to-service calls.

  • REST: resources and HTTP methods. Excellent HTTP caching and tooling. Weakness: over-fetching and chains of calls for complex screens.
  • GraphQL: the client specifies fields in one request to one endpoint. It removes over- and under-fetching. Costs: harder HTTP caching, query cost control, the N+1 problem on the server.
  • gRPC: binary Protocol Buffers over HTTP/2, strict contracts, streaming. Not callable from browsers without gRPC-Web and a proxy.

Typical architecture. gRPC between services, a BFF or gateway in front, and REST or GraphQL to the browser. The choices combine.

Q14. Why can't browsers call gRPC directly?

Short answer. gRPC needs control over HTTP/2 that browser APIs do not give. fetch and XHR hide frames, and gRPC sends its final status in HTTP/2 trailers.

  • Trailers and framing: gRPC messages and statuses rely on low-level HTTP/2 behaviour that scripts cannot access.
  • gRPC-Web: a browser-friendly variant that puts the status in the body. A proxy (commonly Envoy) translates gRPC-Web to native gRPC.
  • Limits: unary and server-streaming calls work; client streaming and bidirectional streaming are not available from the browser.

Consequence. Teams often keep gRPC inside the backend and expose REST or GraphQL to the browser through a gateway or BFF, or accept the proxy and the streaming limits. Newer protocols that work in browsers exist; check current support (VERIFY).

Q15. How do you handle failed requests and rate limits on the client?

Short answer. Classify the failure, then react: retry what is transient and safe, stop on what is not, and always keep the user informed.

  • Always: set a timeout, support cancellation, and check res.ok.
  • Network error or 5xx: retry idempotent requests with exponential backoff and jitter, a small attempt cap, and a visible error at the end. Non-idempotent requests need an idempotency key.
  • 429: wait for Retry-After, then retry. Reduce your own call rate: batch, debounce, deduplicate.
  • 4xx (not 429): do not retry. Show validation errors, or refresh credentials once on 401.
  • Offline: show cached data, queue user actions and replay them in order on reconnect.

Put it in one place. An API client layer applies these rules for every call, so components stay simple.

Q16. What is a Backend-for-Frontend (BFF), and why use one?

Short answer. A BFF is a small backend dedicated to one frontend (web, iOS, Android). It aggregates internal services and returns exactly what that client's screens need.

  • Problem it solves: internal APIs are general-purpose. A screen may need five calls and ten times more data than it shows, which hurts on mobile networks.
  • What it does: calls services in parallel, merges and trims the data, hides internal protocols (for example gRPC), and can hold session or token handling.
  • Patterns: it acts as a Facade (one simple interface) and an Adapter (internal shape to UI shape).
  • Ownership benefit: the frontend team owns it and can change responses without waiting on several backend teams.

Trade-offs. One more service to run, and risk of duplicated logic between BFFs. An API gateway complements it by handling cross-cutting concerns such as auth and rate limits at the edge.

Q17. How would you design reconnection logic for a chat application?

Short answer. Detect failure quickly, reconnect with jittered exponential backoff, resume from the last message seen, and make message handling idempotent.

  1. Detect: listen for close, and run an application heartbeat (ping and pong). If no pong arrives in a few seconds, close the socket and treat it as down.
  2. Reconnect: wait a random time up to min(cap, base x 2^attempt). Reset the attempt count after a successful connection. Pause while the browser is offline and retry when the online event fires.
  3. Resume: every server message has an increasing sequence number. On connect, the client sends the last one it processed, and the server replays what was missed. If the gap is too large, refetch history over REST.
  4. Deduplicate: ignore any message with a sequence number already seen. Give each outgoing message a client id, keep it pending until acknowledged, and resend with the same id.
  5. UI: show "reconnecting", keep unsent messages visible, and share a single socket across the app.

Server side. Spread reconnects with jitter to avoid a thundering herd, and use a Pub/Sub broker so any server can deliver to any user.

Q18. Which protocol would you choose for a live stock ticker, and how would you build it?

Short answer. SSE or WebSocket, with the server coalescing updates. I would start with SSE because data flows one way, and move to WebSocket if the client needs to send frequent subscription changes.

  • Transport: SSE gives automatic reconnect and plain HTTP. WebSocket suits two-way control messages or binary payloads. Over HTTP/1.1, watch the six-connection limit, so use one stream and multiplex symbols inside it.
  • Rate control: price feeds are faster than the eye. The server keeps only the latest price per symbol and sends it every 100 to 250 ms. The client updates only changed rows.
  • Reconnect: send a fresh snapshot, not missed ticks, because old prices have no value.
  • Subscriptions: subscribe only to symbols on screen, and unsubscribe when they scroll away.
  • Scale: many socket servers behind a load balancer, fed by a Pub/Sub broker. Fan-out is the cost, so consider sending deltas.
  • Backup: a REST endpoint for the snapshot and a polling fallback when streaming is blocked.

Speed rules

  • Small requests: cut round trips. Big responses: cut bytes.
  • Page load chain: DNS, TCP, TLS 1.3 (1 RTT), HTTP.
  • Reuse connections (keep-alive), use a CDN, enable HTTP/2 and HTTP/3.

HTTP

  • Safe: GET, HEAD, OPTIONS. Idempotent: GET, PUT, DELETE. POST is neither.
  • 2xx ok, 3xx redirect, 4xx client, 5xx server. fetch does not reject on 4xx or 5xx.
  • Fresh: max-age. Stale: ETag, then 304. no-store means never store.
  • Non-simple cross-origin request: preflight (OPTIONS). CORS is browser-enforced.

Live updates

  • Rare updates: polling. Server to client: SSE. Two-way and frequent: WebSocket. Calls and P2P: WebRTC.
  • Reconnect: heartbeat, jittered backoff, resume by sequence, dedupe.

APIs

  • REST: cacheable and simple. GraphQL: flexible, watch N+1 and cost. gRPC: service to service, needs gRPC-Web in browsers.
  • Lists: cursor pagination. POST retries: Idempotency-Key.
  • BFF per client, gateway at the edge.

Resilience

  • Timeout and abort every request. Retry only transient and safe failures.
  • 429: honour Retry-After. Dedupe, batch, debounce. Queue while offline.
